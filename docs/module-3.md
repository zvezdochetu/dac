# Модуль 3. Ветвление и другие возможности Git

??? tip "Если что-то пошло совсем не так: как сделать сброс вашего репозитория"

    Если при работе с Git вы столкнулись с ошибкой, которую не можете разрешить, можно сделать «глобальный Ctrl+Z». При этом локальный репозиторий в точности скопирует состояние удаленного репозитория.

    Это экстренная мера, удаляющая все ваши локальные изменения.
    На удаленный репозиторий это не повлияет.

    Чтобы сделать сброс локального репозитория, последовательно выполните команды:

    ```
    git fetch origin
    ```
    ```
    git reset --hard origin/main
    ```

## Практика 2: отправка на стейдж

1. Проверьте состояние Git (`git status`).

1. Откройте в VS Code два md-файла, из которых собираются страницы [Docker Build Cloud setup](https://zvezdochetu.github.io/docker-docs-course/build-cloud/setup/) и [Uninstall Docker Desktop](https://zvezdochetu.github.io/docker-docs-course/desktop/uninstall/). Для этого используйте строку Command Center.

1. Измените открытые файлы `content\manuals\build-cloud\setup.md` и `content\manuals\desktop\uninstall.md` и сохраните изменения.

1. Проверьте, как изменилось состояние Git (`git status`).

1. Отправьте оба измененных файла на стейдж:

    ```
    git add .
    ```

1. Еще раз проверьте, как изменилось состояние Git.

1. Удалите файл `uninstall.md` со стейджа:

    ```
    git restore --staged content\manuals\desktop\uninstall.md
    ```

1. И опять проверьте состояние Git :)

1. Откатите изменения в файле `uninstall.md`:

    ```
    git restore content\manuals\desktop\uninstall.md
    ```

1. Ну и как обычно, проверьте состояние Git :)

1. Откройте вкладку Source Control на левой панели и проверьте, что файл `setup.md` отображается в области Staged Changes. Уберите его со стейджа (правая кнопка мыши, **Unstage Changes**), а затем снова поместите на стейдж (правая кнопка мыши, **Stage Changes**).

**Шпаргалка по командам:**

??? info "Отмена локальных изменений (Restore)"

    Если вы по ошибке изменили файл в локальном репозитории, можно вернуть его в исходное состояние:

    - Если измененный файл не был сохранен, нажимайте **Ctrl+Z** до полной отмены изменений, а затем сохраните файл (**Ctrl+S**).

    - Если измененный файл уже был сохранен, выполните команду:

        ```
        git restore <имя_файла>
        ```

        !!! tip "Совет"

            Чтобы отменить изменения во всех файлах, выполните команду:

            ```
            git restore .
            ```

    - Если измененный файл был не только сохранен, но и добавлен на стейдж, последовательно выполните команды:

        ```
        git restore --staged <имя_файла>
        ```
        ```
        git restore <имя_файла>
        ```

??? info "Стейдж (Staging Area)"

    Если один или несколько файлов изменены и сохранены, их можно отправить на стейдж (Staging Area).

    Добавление файла на стейдж:

    ```
    git add <имя_файла>
    ```

    Добавление всех измененных файлов на стейдж:

    ```
    git add .
    ```

    Удаление файла со стейджа:

    ```
    git restore --staged <имя_файла>
    ```

    Удаление всех файлов со стейджа:

    ```
    git restore --staged .
    ```

## Практика 3: создание коммита





**Шпаргалка по командам:**

??? info "Коммит (Commit)"

    !!! warning "Внимание"

        Не делайте коммиты в ветку `main` и не вливайте в нее другие ветки. 

    Создать коммит:

    ```
    git commit -m "заголовок коммита"
    ```

    Исправить заголовок последнего локального коммита:

    ```
    git commit --amend -m "правильный заголовок коммита"
    ```

    Удалить коммит из текущей ветки и вернуть все изменения на стейдж:

    ```
    git reset --soft HEAD~1
    ```

## Практика 5: работа с ветками





**Шпаргалка по командам:**

??? info "Работа с ветками"

    !!! warning "Внимание"

        1. Перед созданием новой ветки проверьте, что вы находитесь на ветке `main`.
        1. Перед переключением ветки сохраните все изменения и сделайте коммит (или отмените изменения).

    Просмотр информации о локальных ветках:

    ```
    git branch
    ```

    Создание ветки:

    ```
    git switch -c <имя_ветки>
    ```

    Переключение на другую ветку:

    ```
    git switch <имя_ветки>
    ```

    Чтобы переключиться на предыдущую ветку, можно использовать краткий синтаксис:

    ```
    git switch -
    ```

    Для безопасного удаления ветки переключитесь на ветку `main` и выполните:

    ```
    git branch -d <имя_ветки>
    ```

    Для принудительного удаления ветки, в которой остались невлитые коммиты, переключитесь на ветку `main` и выполните:

    ```
    git branch -D <имя_ветки>
    ```

    Для вливания (Merge) ветки `main` в текущую:

    ```
    git merge main
    ```

    Отмена слияния:

    ```
    git merge --abort
    ```

## Практика 6: отправка изменений на сервер




**Шпаргалка по командам:**

??? info "Отправка (Push) и вытягивание (Pull) изменений с сервера"

    Если вы создали новую локальную ветку и сделали первый коммит, для его отправки на сервер выполните:

    ```
    git push -u origin <имя_ветки>
    ```

    После первого `push` ветка на сервере уже создана и привязана. Поэтому далее используйте краткую форму:

    ```
    git push
    ```

    Чтобы обновить локальную ветку `main` («принести состояние с сервера»), переключитесь на нее и выполните:

    ```
    git pull
    ```

## Важные замечания

В каждом проекте есть свой регламент работы с Git:

* **Альтернативные команды Git:** одну и ту же задачу можно решать разным набором команд — например, использовать классическую `git checkout` вместо более новых `git switch` и `git restore`.
* **Запрещенные команды Git:** некоторые операции могут быть строго запрещены (например, `git push --force` или `git rebase` в общих ветках) или требовать обязательных флагов.
* **Стандарты названий и заголовков:** названия веток (например, `feature/login`), формат коммитов и имя главной ветки (`main`, `master` или `production`) обычно строго заданы регламентом проекта.
